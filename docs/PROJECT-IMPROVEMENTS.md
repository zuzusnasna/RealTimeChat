# 개선 이력 및 현재 상태

이 문서는 기능 개선, 성능 측정, 되돌린 시도와 미해결 항목을 구분해 기록합니다. 측정 결과는 기록된 실행 환경에 한정되며 운영 환경의 성능을 보장하지 않습니다.

## 주요 기능 개선

- **인증 및 접근 제어**: 회원가입·로그인·로그아웃, HTTP 세션 인증, 채팅방 참여 권한 검증을 적용했습니다.
- **실시간 채팅**: WebSocket/STOMP를 이용해 메시지를 송수신하고 MySQL에 저장합니다.
- **다중 인스턴스 메시지 전달**: Redis Pub/Sub으로 app-1과 app-2 사이에 채팅 메시지와 읽음 상태를 전달합니다.
- **읽음 상태**: 마지막으로 읽은 메시지 위치와 미읽음 인원 수를 표시합니다.
- **프로필 및 메시지 표시**: 닉네임 변경과 현재 닉네임 표시, 메시지 본문의 URL 링크 처리를 추가했습니다.
- **초기 이력과 실시간 이벤트 병합**: 방 진입 시 메시지 이력과 실시간 수신 이벤트가 겹치는 문제를 줄이기 위한 병합 처리를 추가했습니다.
- **로컬 개발 환경**: 로컬 MySQL을 호스트 포트 3307로 분리하고 `start-local.ps1` / `stop-local.ps1`로 프론트엔드·백엔드 실행을 관리합니다.
- **운영 자원 설정**: Prometheus/Grafana를 Compose의 `monitoring` 프로필로 분리하고, 앱별 JVM 메모리 제한 및 HikariCP 연결 풀 상한을 설정했습니다. SQL 출력은 기본 비활성화이며 환경 변수로 켤 수 있습니다.

## 성능 개선 및 측정 결과

### DB 행 잠금 제거

채팅 메시지 저장 경로에 있던 채팅방 행의 비관적 쓰기 잠금을 제거했습니다. 이 잠금은 동일 방의 동시 메시지 전송을 직렬화해 지연을 키울 수 있었으므로, 성능 측정 후 제거했습니다. **성능 개선을 위해 이 잠금을 다시 추가하지 않습니다.**

| 실행 환경 | 테스트 조건 | 전송 / 수신 | 평균 전달 시간 | p95 | 최대 |
|---|---|---:|---:|---:|---:|
| 로컬 | 2 VU, 30초, 250ms 간격 | 232 / 232 | 26.42ms | 39.69ms | 494ms |
| EC2 | 2 VU, 30초, 250ms 간격 | 232 / 232 | 27.3ms | 68.69ms | 277ms |
| EC2 | 2 VU, 60초, 100ms 간격 | 1158 / 1158 | 18.96ms | 34ms | 171ms |

위 수치는 당시 실행 결과입니다. 특히 최대 지연과 p95는 부하, 호스트 자원, 테스트 시점에 따라 달라질 수 있습니다.

### EC2 자원 사용

EC2에서 메모리 및 Swap 압박이 관측되어 모니터링 컨테이너를 기본 실행 대상에서 분리했습니다. 앱 2개, MySQL, Redis, Nginx를 기본으로 실행하고, Prometheus/Grafana는 필요할 때만 프로필로 실행합니다.

## 메시지 순서: 미해결

부하 테스트에서는 전달 지연이 개선된 이후에도 메시지 순서 역전과 도착 시점의 sequence gap이 관측됐습니다. 가장 강한 기록 테스트에서는 1158건 전송·수신, 평균 18.96ms, p95 34ms였지만 순서 역전 6건과 gap 6건이 기록됐습니다.

Redis listener를 단일 스레드 executor로 직렬화하는 시도를 했으나, 로컬 2 VU / 60초 / 100ms 테스트에서 다음 결과가 나와 되돌렸습니다.

- 전송 1117건, 수신 1080건
- 평균 전달 시간 91.98ms, p95 567.74ms, 최대 2.19초
- 관측된 순서 역전 23건, gap 21건

따라서 단일 스레드 listener 방식은 현재 해결책으로 채택하지 않습니다. 해당 변경은 `main`에서 되돌렸습니다. 위의 gap 카운터는 테스트 코드상 더 늦게 도착한 메시지가 나중에 보완되더라도 당시 gap 관측치를 취소하지 않을 수 있으므로, 실제 유실과 순서 역전을 구분해 테스트 로직도 검토해야 합니다.

### 다음 작업 순서

1. **메시지 순서 문제의 재현 조건과 k6 측정 로직을 확인**하고, 실제 유실·중복·역전을 구분합니다.
2. 클라이언트 → STOMP 컨트롤러 → DB 저장 → Redis 발행/수신 → WebSocket 전송 흐름을 추적합니다.
3. 여러 앱 인스턴스에서 방 단위 순서를 보장할 방법을 설계하고, 지연 성능 회귀가 없는지 로컬에서 검증합니다.
4. 기능 브랜치에서 테스트한 뒤 사용자 확인 후에만 `main`에 병합·배포합니다.

## 운영 및 개발 원칙

- `main`에 직접 검증되지 않은 변경을 넣지 않고, 기능 브랜치에서 테스트한 뒤 병합합니다.
- DB 데이터가 포함될 수 있는 볼륨을 `docker compose down -v`로 삭제하지 않습니다.
- 성능 최적화는 동일 조건의 k6 결과와 앱/호스트 지표를 함께 비교합니다.
- 메시지 순서 보장은 별도 검증이 통과하기 전까지 완료로 표시하지 않습니다.
