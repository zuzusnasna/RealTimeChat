# EC2 채팅 지연 및 자원 사용 분석

- 분석일: 2026-10-23
- 대상: `zuzusnasna/RealTimeChat` EC2 배포
- 목적: 메시지 지연과 인스턴스 메모리 압박을 줄이고, 이후 메시지 순서 역전을 검증한다.
- 범위: 사용자가 제공한 EC2 명령 출력, 기존 k6 결과, 저장소의 Compose/JVM/채팅 코드 검토
- 주의: 이 문서는 관측된 사실과 추정 및 변경 계획을 구분한다. 단일 원인이 확정된 것은 아니다.

## 1. 요약

현재 EC2에서 메모리 압박과 간헐적인 메시지 지연이 관측됐다. app-2는 컨테이너 메모리 한도에 가까운 RSS를 사용했고, app-1은 프로세스 메모리 페이지의 상당 부분이 Swap으로 이동한 상태였다. 이전 2계정 k6 실행에서는 메시지 전달 평균이 약 48.9ms였지만 최대값은 약 2.75초였다.

**가장 먼저 할 일은 운영 기본 설정의 불필요한 SQL 표준 출력과 과도한 DB 연결 풀 상한을 줄이는 것이다.** 이는 위험이 비교적 낮은 자원 사용 최적화이며, 2초 이상 지연의 직접 원인을 해결했다고 단정할 수는 없다.

## 2. 관측 결과

| 항목 | 관측값 | 의미 |
|---|---:|---|
| 호스트 RAM | 약 908 MiB | 메모리 예산이 매우 제한적 |
| 호스트 Swap 사용 | 약 1 GiB 전후 | 메모리 압박이 존재 |
| app-1 RSS | 약 27 MiB | 측정 시점에 상주 메모리가 적음 |
| app-1 VmSwap | 약 282 MiB | 프로세스 페이지가 Swap에 많이 이동함 |
| app-2 RSS | 약 257 MiB | 컨테이너 한도 288 MiB에 근접 |
| app-2 cgroup memory.events | max 650, oom 0, oom_kill 0 | 메모리 한도 이벤트가 있었으나 OOM 종료는 관측되지 않음 |
| Java 스레드 | 인스턴스당 51 | 스레드 수만으로 병목을 확정할 수 없음 |
| Redis Slow Log | 관측된 명령은 대체로 수십 ms 이내 | Redis 명령 실행 자체가 다중 초 지연의 주원인이라는 증거는 부족 |
| 2계정 k6 전달 시간 | 평균 약 48.9ms, 최대 약 2.75s | 전반적으로 빠르지만 꼬리 지연이 존재 |
| k6 수신 | 전송 402건, 수신 401건으로 기록됨 | 해당 실행만으로 순서 보장 및 완전 전달을 확정할 수 없음 |

### 해석 시 주의점

- `VmSwap`은 Java 힙 사용량이 아니다. RSS와 더해서 실제 RAM 사용량으로 계산하면 안 된다.
- `memory.events max`는 한도에 도달하려 한 누적 이벤트이며 OOM 발생 횟수와 같지 않다.
- GC 로그에서 `Using ... GC` 설정 문구만 확인됐고, 실제 GC pause 또는 Full GC 로그는 확인되지 않았다.
- 한 번의 `redisPublishMs` 급증만으로 Redis 서버를 원인으로 확정할 수 없다. 발행 호출 전후의 스레드 스케줄링, 호스트 자원 압박, 네트워크 대기 가능성도 남아 있다.

## 3. 코드 및 설정에서 확인한 사항

1. `spring.jpa.show-sql=true`와 `hibernate.format_sql=true`가 기본 설정으로 활성화되어 있다. SQL 로그는 운영 stdout/log 수집량과 포맷 비용을 늘릴 수 있으므로 기본값을 끄고 필요할 때 환경 변수로 켜는 편이 낫다.
2. HikariCP 연결 풀 크기를 명시하지 않아 Spring Boot 기본 상한에 의존한다. 앱이 2개라 기본 상한이 각각 적용될 수 있다. 작은 EC2에서는 연결 풀을 보수적으로 제한하는 것이 합리적이지만, 부하가 커지면 풀 대기가 늘 수 있으므로 부하 테스트가 필요하다.
3. 메시지는 DB에 저장된 후 컨트롤러에서 Redis Pub/Sub로 발행된다. DB 저장/트랜잭션 종료와 발행 사이의 동시 실행 때문에 DB ID 순서가 클라이언트 도착 순서와 항상 같다고 보장할 수는 없다. 순서 보장은 별도 수정 및 테스트가 필요하다.
4. Nginx는 `ip_hash`로 HTTP 세션을 같은 앱 인스턴스에 고정한다. 앱 한 대를 끄는 방식은 가용성과 세션/라우팅 영향이 있으므로 자동으로 적용하지 않는다.

## 4. 적용할 저위험 설정 변경

- SQL 출력 기본값을 끈다. `JPA_SHOW_SQL=true` 및 `JPA_FORMAT_SQL=true`로 필요 시 다시 활성화할 수 있게 한다.
- HikariCP 풀 기본값을 인스턴스당 최대 4개, 최소 유휴 연결 1개로 명시한다. 환경 변수 `DB_POOL_MAX_SIZE` 및 `DB_POOL_MIN_IDLE`로 조정 가능하게 한다.
- JVM 힙/메타스페이스 한도는 현재 로그만으로 안전한 최적값을 확정할 수 없어 이번 변경에서 임의로 줄이지 않는다.
- 앱 인스턴스 수, 컨테이너 메모리 제한, Redis Pub/Sub 경로는 이번 변경에서 변경하지 않는다.

## 5. 검증 계획

1. PR CI에서 Gradle 테스트 및 빌드 성공 여부를 확인한다.
2. 사용자가 기능 브랜치를 로컬에서 받아 두 계정으로 로그인/채팅/읽음 처리와 빠른 연속 메시지 전송을 확인한다.
3. 병합 전후 같은 방/계정/메시지 수로 k6를 실행해 평균, p95, 최대 지연, 송신/수신 수, 순서 역전을 비교한다.
4. EC2 배포 후 `MemAvailable`, Swap, 컨테이너 RSS, Hikari 풀 대기, 채팅 지연을 비교한다.
5. 지연이 계속되면 다음 단계에서 DB row lock 대기, 트랜잭션 시간, Redis 발행, listener/STOMP 전송을 분리해 확인한다. 메시지 순서 문제는 별도 테스트를 통과하기 전까지 해결된 것으로 표시하지 않는다.

## 6. 결론

메모리 압박은 관측된 문제지만, 다중 초 메시지 지연의 단일 원인은 아직 확정되지 않았다. 이번 변경은 불필요한 SQL 출력과 DB 연결 풀의 기본 상한을 줄이는 보수적 최적화다. 성능 향상 여부는 동일 조건의 테스트로 확인해야 하며, 메시지 순서 보장은 후속 과제로 남긴다.
